# LinkDigest V0.3 SQLite Binding、迁移与恢复 Spike

> 状态：实施完成，等待独立 Sol 审查。候选结论为 **ACCEPT（SwiftPM 门禁）**；`pnpm xcode:build` 的首个 Xcode scheme 仍被 Hana 外层环境的 nested sandbox `sandbox_apply: Operation not permitted` 阻断，作为 RC 前未关闭证据单列，不归因于 GRDB。

## 1. 任务卡

- 任务名称：P0-RC-01 SQLite Binding、迁移与恢复 Spike
- 用户场景：LinkDigest 后续要把本地历史交给 SQLite；在正式四表 Repository 和历史 UI 开工前，先证明底层零件能安全迁移、并发、备份和故障降级。
- 本次只解决：比较并冻结一个 Swift SQLite binding 候选，建立隔离 persistence target，以最小两表夹具验证基础能力。
- 明确不做：正式 `Task/ContentSnapshot/Run/Artifact` schema、Repository、历史 Sidebar、导出 UI、Capture/Provider/Native Host 行为、签名、公证或发布。
- 数据边界：全部测试与 benchmark 使用物理临时目录；没有调用真实 Application Support、浏览器资料、Keychain 或 Provider。

## 2. 场景、角色与交接

```text
未来 Application Service
  ↓ 交接：领域命令或 Repository Port（本 spike 尚未接线）
LinkDigestPersistence
  职责：路径、事务、WAL、迁移、备份、只读恢复
  ↓ 交接：安全状态、计数、脱敏 projection
GRDB 7.11.1
  职责：把 Swift 调用翻译为 SQLite API，管理连接池与 Online Backup
  ↓
系统 SQLite
  职责：事务日志、锁、页面、完整性检查
```

- 入口：本任务只有 tests、benchmark executable 和未来 adapter 调用点，没有 SwiftUI 入口。
- 交接边界：GRDB 类型只存在于 `LinkDigestPersistence` 内部；`LinkDigestCore`、View、ViewModel 与现有 App target 都没有依赖该 target。
- 失败可见语义：未来 schema、迁移失败、存储不可写分别进入具名只读原因；错误字符串不含完整本机路径。

## 3. 本次五个名词

| 名词 | 人话解释 | 生活类比 | 项目位置 | 没有它会怎样 | 等级 |
|---|---|---|---|---|---|
| Binding | Swift 与 SQLite C 引擎之间的翻译层 | 双语柜台 | `LinkDigestPersistence` 内部 | 每个连接、参数和错误都要手写 C 封装 | L3 |
| WAL | 先把已提交变更追加到旁边日志，再择机归并主库 | 仓库的当日流水账 | 数据库同目录 `-wal` | 读写更容易互相阻塞 | L3 |

| Read-only Recovery | 写入有风险时保留读取与导出逃生口 | 仓库封存后仍允许盘点取件 | `SQLiteSpikeAccessMode.readOnly` | 只能冒险写入或删库重来 | L3 |

| 候选 | 版本 / 许可证 | 默认传递包 | Swift / Xcode | Migration | WAL / 并发 | Online Backup | 只读打开 | 维护成本 | 结论 |
|---|---|---:|---|---|---|---|---|---|---|
| GRDB | 7.11.1 / MIT | 0；tag 的 `Package.swift` 仅在 `SPI_BUILDER=1` 加 docc plugin | Swift 6.1+ / Xcode 16.3+ | `DatabaseMigrator` 与事务化迁移；本 spike用更小的 `user_version` 前向包装 | `DatabasePool` 自动 WAL，单 writer + 多 reader | 直接封装 SQLite Online Backup API | `Configuration.readonly` | 最低；恢复策略仍由产品包装 | **选择** |

## 5. 实际范围与 schema

`LinkDigestPersistence` 的两张表只用于 spike：

- v001：`spike_items`、`spike_notes` 与外键索引。
- v002：为 `spike_items` 增加 `rank_key` 与首页排序索引。

它们不使用正式领域名称，不承诺字段、删除语义或索引可迁移到后续四表 schema。正式 migration 001 仍需单独冻结 UUID、UTC、幂等键和删除语义。

数据库位置由 `SQLiteSpikeLocation` 接收一个专属目录；测试把它放在临时根下的 `Application Support/LinkDigest` 形状中，并断言 `db`、`-wal`、`-shm` 同目录。模块没有自行查询或写入真实用户 Application Support。

## 6. 失败与恢复设计

| 场景 | 写入 | 读取 / projection | 恢复 |
|---|---|---|---|
| 空库、v001、v002 | 迁移成功后可写 | 可读 | 只向前到 v002 |
| future schema | 拒绝 | 数据可读时允许 | 升级支持该 schema 的 App；当前不降级、不删库 |
| v002 注入失败 | 事务回滚，保持 v001 | 进入 `migration_failed` 只读 | 修复迁移后重开；原库保留 |
| 文件或目录不可写 | 拒绝 | 数据可读时允许 | 修复存储权限后重开 |
| 双记录第二步失败 | 两条都回滚 | 既有数据不变 | 重试整个事务 |
| 活跃 WAL 备份 | 源库继续可用 | 备份为一致快照 | Online Backup 后把“目标备份”转为 DELETE journal 单文件，再用 Online Backup 恢复 |

恢复错误只暴露固定类别。测试明确断言错误描述不包含临时数据库的完整路径。

### 6.1 被测试修正的两点

1. 首轮把 GRDB `DatabasePool.write` 外又套 `inTransaction`，触发嵌套事务错误。修正为只使用 `write` 的自动事务；抛错仍自动回滚。
2. 首轮 Online Backup 内容一致，但备份目标继承 WAL mode，独立只读打开时没有伴随 `-wal/-shm`。修正为只在备份目标连接上切回 DELETE journal，使其成为独立单文件；活跃源库保持 WAL，没有文件复制。

## 7. 自动验证

### 7.1 Persistence tests

`pnpm sqlite:spike` 对应 12 项测试：

- 空库 → latest、v001 → latest、v002 → latest。
- future schema 只读、migration 注入失败不半迁移且不删库。
- 双记录事务成功与第二步失败全回滚。
- WAL mode、`-wal` 可观察、PASSIVE checkpoint frame 可观察。
- 活跃库 Online Backup、受控恢复、`integrity_check = ok`、40/40 计数。
- 文件/目录不可写只读恢复与空目录零写入。
- 1 writer + 8 readers，200 次双记录写入，10 秒有界等待，无死锁、丢写或计数分叉。
- db / wal / shm 专属目录语义与错误路径脱敏。

结果：12 tests，0 failures。

### 7.2 10k Release benchmark

命令：`pnpm sqlite:benchmark:release`

- 独立临时库；固定 seed `20260715`。
- 10,000 个 `spike_items` 与 10,000 个必要关联 `spike_notes`。
- 最近历史首页 50 条与单项详情各预热一次，再各采集 30 个 raw samples。
- JSON 不含正文、URL 或绝对路径。
- 完整 raw evidence：`docs/evidence/V0.3_SQLITE_BENCHMARK_2026-07-15.json`。

| 查询 | p50 | p95 | max | 门槛 |
|---|---:|---:|---:|---:|
| 最近历史首页 | 0.036917 ms | 0.048000 ms | 0.051542 ms | ≤ 300 ms |

## 8. 回滚方法

本任务没有数据格式进入真实用户目录，回滚只需由后续负责人移除：

1. `Package.swift` 中 GRDB exact dependency、`LinkDigestPersistence`、benchmark product/target 和 test target。
2. `Package.resolved` 中唯一 GRDB pin。
3. 新增 persistence / benchmark / tests 目录、Swift license check、根 scripts 与本规格/证据文档。

不得通过删除真实数据库回滚；本 spike 从未创建真实用户数据库。现有 V0.1、Brain 与 Capture/Provider/Native Host 改动不属于本任务，回滚时不得触碰。

## 9. 验收结论与未关闭风险

### 候选结论：ACCEPT（待独立 Sol 审查）

许可证、SwiftPM Debug/Release、事务、WAL、checkpoint、Online Backup/恢复、migration/只读恢复、1+8 并发和 10k p95 均通过，因此 GRDB 7.11.1 可以作为后续正式 persistence adapter 的优先 binding。

未关闭风险：

1. Xcode 集成构建在当前 Hana 外层环境中被 nested sandbox 阻断；这是 RC 前仍需在无该外层限制环境补齐的证据，不能写成已通过，也不构成 GRDB 功能失败。
2. 完整 Swift suite 的既有 Network.framework、Keychain 与 socket 测试在当前外层环境有 10 项失败；persistence 12/12独立通过。RC 仍需在正常本机环境补齐完整 suite 全绿证据。
3. 正式四表 schema、Repository Port、真实 Application Support 创建/升级、长正文规模、删除语义和导出逃生口尚未实施。
4. GRDB 的 MIT notice 必须随商业分发的第三方 notices 一并保留。
5. benchmark 是本机固定夹具热查询，正式 schema 完成后必须重跑同门槛。
