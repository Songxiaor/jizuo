## 1. 任务卡与用户场景

- **用户场景**：用户已经把当前网页正文送入 APP，希望使用自己的模型连接生成总结或翻译。
- **本轮只解决**：把 V0.2 拆成可实现、可测试、可讲解的组件与后续任务。
- **当前状态**：任务 A–D 已实现并形成集中验收证据；当前正文可以形成总结/翻译 intent，经 Orchestrator 与 adapter 进入 streaming UI，并支持停止、完成、不完整、失败和统一恢复动作。

最小用户路径：

```text
用户已经通过 V0.1 把当前网页正文发送到 APP
  → 用户配置 OpenAI-compatible Base URL / API Key / 模型名
  → APP 把非敏感配置与 Keychain secret 分开保存
  → 用户点击总结或翻译
  → APP 通过 URLSession 发起 Chat Completions streaming 请求
  → 用户看到进行中的结果
  → 用户可以停止
  → 完成后看到完整结果、部分结果或可恢复错误
```

发布前，第一次发送正文前的界面必须说明：正文会直接发送到用户配置的 Provider，不经过 LinkDigest Cloud。当前界面尚未接入这条数据去向提示，因此它仍是发布准备缺口；这不影响只使用 fake server 的 V0.2 本地工程链路收口，但任何真实 Provider 抽样都必须单独授权并只用非私人正文。

### 1.1 本阶段明确不做

- 多 Provider 管理；只保留一个 active profile。
- Responses API。
- Ollama 或其它本地模型专用协议。
- LinkDigest 账号、Cloud API、同步、托管模型或云端额度。
- SQLite 历史持久化；只保留以后替换 profile store 的接口。
- 导出。
- Q&A。
- 自动分块、长文 Map/Reduce 或上下文窗口优化。
- 正式视觉品牌。
- 修改浏览器扩展与 V0.1 capture contract。

## 2. 当前实现事实与最小新增链路

当前 `AppViewModel` 同时维护 socket/capture 展示与 UI-safe `RunState`；`ModelRunOrchestrator` 已在 Core 中隔离 profile、secret、Provider、取消和 stale run。Keychain、URLSession、SSE 与重试仍不进入 View / ViewModel。

当前已实现的最小链路：

```text
ContentView
  交接：配置动作 / summarize 或 translate intent / stop
        ↓
ModelRunOrchestrator（Application）
  读取：ProviderProfileStore + SecretStore
  调用：ModelProvider
  输出：RunState
        ↓
OpenAICompatibleProvider（Adapter）
  使用：URLSession + Chat Completions streaming
  输出：ModelStreamEvent / AppError
        ↓
AppViewModel（MainActor）
  只把 RunState 映射为 SwiftUI 可见状态
```

V0.2 不修改 `CaptureEnvelopeV1` JSON Schema。模型调用发生在 macOS APP 内部，不新增 Swift/TypeScript 跨语言合同。

## 3. 最小组件边界

| 组件 | 负责 | 接收 | 输出 | 不负责 |
|---|---|---|---|---|
| `ProviderProfile` | 表示单个 active 模型连接的非敏感配置 | Base URL、模型名、API 模式、secret reference | 可校验的连接配置 | 保存完整 API Key、发网络请求、管理多个 Provider |
| `ProviderProfileStore` | 保存和读取非敏感 profile | `ProviderProfile` | 当前 active profile 或未配置状态 | 保存 Key、保存历史结果 |
| `UserDefaultsProviderProfileStore` | V0.2 的本机非敏感 profile adapter | 编码后的 profile | 本机可恢复配置 | 保存秘密；不能成为 Keychain 失败时的降级路径 |
| `SecretStore` | 定义秘密保存、读取、替换和删除的 port | secret reference、secret value | 成功或稳定秘密错误 | 决定 UI 文案、保存非敏感 profile |
| `KeychainSecretStore` | 使用 macOS Keychain 实现 `SecretStore` | API Key 与 opaque reference | Keychain item 或稳定错误 | 把 Key 写入 UserDefaults、SQLite、文件或日志 |
| `ModelProvider` | 定义模型连接测试与流式生成 port | profile、secret、run intent、正文 | 异步 `ModelStreamEvent` | 读取 SwiftUI、Keychain 或 SQLite |
| `OpenAICompatibleProvider` | 组装 Chat Completions 请求并翻译 SSE 事件 | 已校验 profile、短时存在内存中的 Key、prompt | delta、完成、provider usage 或稳定错误 | 管理 UI 状态、保存结果、多 Provider 路由 |
| `ModelRunOrchestrator` | 协调配置、秘密读取、请求、取消和错误映射 | summarize/translate intent、当前 capture | `RunState` 更新 | 直接实现 HTTP、Keychain 或 SwiftUI |
| `RunState` | 描述一次生成的可观察生命周期 | stream event、cancel、mapped error | idle/streaming/completed/incomplete/failed | 发请求或持久化历史 |
| `AppError` 映射 | 把平台/Provider 错误变成稳定 code、retryable、action、safeDetail | HTTP、URLSession、Keychain、SSE 错误 | 用户可恢复错误 | 保存原始响应正文、Header、Key 或页面正文 |

### 3.1 SwiftUI View 的禁止边界

SwiftUI View 不直接：

- 调用 Security/Keychain API。
- 创建或持有 URLSession task。
- 拼接 `/chat/completions` 路径或 Authorization Header。
- 解析 SSE。
- 读写 UserDefaults、SQLite 或文件系统。
- 判断 401、429、5xx 是否重试。
- 持有或回显完整 API Key。

View 只发送用户意图并渲染 `AppViewModel` 暴露的配置状态与 `RunState`。

## 4. 数据与秘密边界

### 4.1 ProviderProfile

V0.2 只有一个 active profile，建议最小字段：

```swift
ProviderProfile(
  id: "default",
  baseURL: URL,
  model: String,
  apiMode: .chatCompletions,
  secretReference: SecretReference
)
```

- `baseURL`、`model`、`apiMode` 与 `secretReference` 是非敏感字段。
- `secretReference` 只是 Keychain item 的 opaque account/id，不能逆推出 Key。
- V0.2 可用 `UserDefaultsProviderProfileStore` 保存这些字段；V0.3 迁入 SQLite 时只替换 adapter。
- 不保存 Provider 返回的原始 Header 或响应正文。

### 4.2 API Key 生命周期

1. 设置页把用户输入的 Key 交给 ViewModel。
2. ViewModel 立即交给 Orchestrator；View 不长期持有 Key。
3. `KeychainSecretStore` 写入成功后才保存/更新 profile 的 secret reference。
4. 请求开始前，Orchestrator 从 Keychain 读取 Key，并只在本次请求内存中短时持有。
5. 请求结束或取消后释放引用，不把 Key 写入任何状态快照。

替换已有 Key 时采用 staged save：先写入新的 Keychain item，再保存引用它的 profile；只有两步都成功后才删除旧 item。若 profile 保存失败，best-effort 删除新 item 并继续保留旧 profile，避免配置指向不存在的秘密。

界面只显示“API Key 已保存”或固定 mask（例如 `••••••••`），不回显完整 Key，也不依赖真实末四位。

如果 Keychain 保存失败：

- 返回 `SECRET_STORE_WRITE_FAILED`。
- 保留用户可重试的设置状态。
- 不保存新的 profile reference。
- 不降级到 UserDefaults、SQLite、剪贴板缓存或明文文件。

### 4.3 禁止进入的边界

完整 API Key 不得进入：

- 普通日志、`safeDetail`、崩溃附加信息。
- UserDefaults、SQLite、导出或项目文件。
- 测试 fixture、快照、截图或 Git。
- ProviderProfile、RunState 或 SwiftUI 可观察对象。

正文、私人 URL 与 Provider 原始响应同样不得进入普通日志。测试中使用明显虚构的 sentinel，并只断言“Header 是否正确”，失败输出不得打印 Header value。

## 5. OpenAI-compatible 请求边界

### 5.1 Base URL 与请求路径

V0.2 把 Base URL 定义为 **API root**，例如：

```text
https://api.example.com/v1
https://openrouter.ai/api/v1
```

规则：

- 只接受 `https`；自动测试可使用 loopback `http://127.0.0.1`。
- 拒绝 userinfo、query 和 fragment。
- 移除多余尾部 `/`，再按 URL path component 追加 `chat/completions`。
- 如果输入已经以 `/chat/completions` 结尾，返回 `MODEL_BASE_URL_INVALID`，不猜测或重复拼接。
- 不通过字符串替换覆盖用户已有的 path prefix。

V0.2 不支持自定义完整 endpoint；真实兼容性抽样证明有必要后再评估。

### 5.2 最小请求

- Method：`POST`。
- Path：`{baseURL}/chat/completions`。
- Header：`Authorization: Bearer <API Key>`、`Content-Type: application/json`、`Accept: text/event-stream`。
- Body 最小字段：`model`、`messages`、`stream: true`。
- `apiMode` 当前只允许 `chat_completions`，但与 Base URL、模型名、Key 分开建模。
- temperature、max tokens 等高级参数在 V0.2 固定为内部默认值，不进入 Provider 管理 UI。

### 5.3 Prompt 使用当前捕获正文

`RunIntent` 只规划两种：

- `summarize`：system message 要求忠于输入、区分已知与不完整信息；user message 放入标题与正文。
- `translate(targetLanguage)`：system message 要求只翻译捕获内容并保留结构；user message 放入正文。

不把 Cookie、Header、API Key 或不必要的完整 URL 放进 prompt。V0.2 不自动分块；如果 Provider 拒绝长度，映射为 `MODEL_INPUT_TOO_LARGE`，提示用户改用选区或较短页面。

### 5.4 Streaming → RunState

`OpenAICompatibleProvider` 把 SSE `data:` 行翻译为：

```swift
ModelStreamEvent.delta(String)
ModelStreamEvent.completed
```

Orchestrator 负责把事件映射为：

```text
idle
  → starting
  → streaming(partialText)
  → completed(text)
  → incomplete(partialText, reason)
  → failed(AppError)              // 尚无任何输出时
```

收到 `[DONE]` 或兼容的明确结束原因后才标记完整。流已产生内容后发生网络、协议或 Provider 中断，保留 partial text 并标记 `incomplete`，不得自动把另一次请求的续写拼接上去。

### 5.5 Stop / Cancel

- Orchestrator 持有当前受控 Task 和 run identifier。
- 用户点击停止后先把状态变为 `stopping`，再向底层 Task 传播 cancellation。
- `OpenAICompatibleProvider` 必须取消对应 URLSession task/bytes sequence。
- 终止后以 `stopped(partialText, incomplete: true)` 收口；用户停止不是 401/网络类错误。
- ViewModel 只接受当前 run identifier 的事件；取消后的迟到 delta 必须丢弃。
- 停止到 UI 不再增长的目标沿用 PRD：≤ 500 ms。

### 5.6 稳定错误与重试

| 场景 | 稳定 code | 自动重试 | 用户恢复 |
|---|---|---:|---|
| 未配置 profile 或 secret | `MODEL_NOT_CONFIGURED` | 否 | 打开设置 |
| Keychain 保存失败 | `SECRET_STORE_WRITE_FAILED` | 否 | 重试保存；不降级明文 |
| Keychain 读取失败/项目不存在 | `SECRET_STORE_READ_FAILED` | 否 | 重新保存 Key |
| Base URL 不合法 | `MODEL_BASE_URL_INVALID` | 否 | 修正 API root |
| 401 | `MODEL_AUTH_INVALID` | 0 次 | 更新 Key 后手动重试 |
| 404/不支持路径 | `MODEL_ENDPOINT_NOT_FOUND` | 0 次 | 检查 Base URL 与 API 模式 |
| 429 | `MODEL_RATE_LIMITED` | 输出前最多 2 次 | 等待后手动重试 |
| 5xx | `MODEL_PROVIDER_UNAVAILABLE` | 输出前最多 2 次 | 稍后重试 |
| 网络中断 | `MODEL_NETWORK_INTERRUPTED` | 默认不自动重试 | 检查网络；有 partial 则保留 |
| Content-Type/协议不兼容 | `MODEL_PROTOCOL_INCOMPATIBLE` | 否 | 检查端点兼容性 |
| malformed SSE/JSON | `MODEL_STREAM_MALFORMED` | 否 | 保留 partial，检查 Provider |
| 输入超过端点能力 | `MODEL_INPUT_TOO_LARGE` | 否 | 改用选区或较短页面 |

这些 code 是 macOS Application 内部的稳定错误词汇，不写入 `capture-envelope-v1.schema.json`，也不通过 V0.1 Native Messaging 返回给扩展。Provider 原始错误只能经过映射后进入 UI。

有界重试规则：

- 429/5xx 仅在尚未收到任何 content delta 时重试。
- 首次请求之外最多再尝试 2 次。
- 优先使用可解析且不超过 10 秒的 `Retry-After`；否则使用 1 秒、2 秒退避并加入小幅 jitter。
- 一旦收到 delta，任何中断都转成 incomplete，不自动重新请求。
- retry clock/backoff 必须可注入，保证测试不真实等待。

`safeDetail` 只能包含 allowlist 后的状态信息，例如 HTTP status、错误类别和脱敏 request id；不得直接放入 Provider response body。

## 6. UI 状态与恢复路径

### 6.1 配置状态

| 用户可见状态 | 展示 | 恢复动作 |
|---|---|---|
| 未配置模型 | Base URL、模型名、API Key 输入 | 保存配置 |
| 正在保存 | 禁止重复提交 | 等待 |
| Keychain 保存失败 | “无法安全保存 API Key” | 重试；不提供明文降级 |
| 已配置 | Base URL、模型名、固定 masked key 状态 | 编辑或替换 Key |
| 模型连接测试中 | 明确 spinner 与“可能产生极少量 Provider 用量” | 可取消 |
| 测试成功 | 连接可用 | 开始总结/翻译 |
| 401 / Key 无效 | 不展示 Provider 原始 body | 更新 Key |
| 429 / 限流 | 展示稍后重试 | 等待或手动重试 |
| 网络中断 | 展示网络恢复动作 | 检查网络 |
| 协议不兼容 | 展示 Base URL/API 模式检查 | 修改配置 |

连接测试使用同一 adapter，对 fake server 自动验证；真实产品中由用户显式点击，使用不含页面正文的最小请求，并提示可能产生 Provider 用量。

### 6.2 运行状态

| RunState | 用户可见行为 | 可用动作 |
|---|---|---|
| `idle` | 显示总结、翻译按钮 | 发起任务 |
| `starting` | 请求正在建立 | 停止 |
| `streaming(partial)` | 文本持续增长 | 停止 |
| `stopping` | 文本停止增长，等待底层取消确认 | 无重复停止 |
| `stopped(partial)` | 标记“用户已停止 / 结果不完整” | 重新开始 |
| `completed(text)` | 标记完成 | 复制；保存/导出留待后续 |
| `incomplete(partial, reason)` | 保留部分结果并标记不完整 | 查看原因、手动重试 |
| `failed(error)` | 尚无可用输出，显示稳定错误与动作 | 按提示恢复 |

## 7. 实现后的测试基线

任务 A–D 已按以下基线建立自动测试；真实 Provider 与连接测试 UI 仍不在自动验收范围。

### 7.1 已采用的测试替身

- Core 使用 `FakeSecretStore`、`FakeProviderProfileStore` 与 `FakeModelProvider`，验证 Orchestrator，不触碰 Keychain 或网络。
- Adapter 集成测试使用进程内 loopback fake OpenAI-compatible server；优先用 Apple Network.framework/Foundation 构建，不安装外部软件。
- fake server 可脚本化返回 SSE chunks、延迟、401、429、5xx、断流、malformed event 与永不结束的流。
- URLSession 使用 ephemeral configuration，关闭持久 cookie/cache。

### 7.2 场景覆盖与剩余缺口

| 测试 | 关键断言 |
|---|---|
| 成功 streaming | delta 顺序正确，`[DONE]` 后 completed |
| 请求边界 | Base URL path、model、`stream: true` 与 Bearer Header 正确；测试失败不打印 Header value |
| 401 | 只发送 1 次，映射 `MODEL_AUTH_INVALID` |
| 429 / 5xx | 输出前最多 3 次总尝试；超过上限停止 |
| 已有 delta 后 429/5xx/断流 | 不自动重试，保留 partial 并标记 incomplete |
| 用户取消 | Orchestrator 调用 Provider 显式取消入口；producer task 在 500 ms 内退出，取消后 UI 不再追加 delta |
| Keychain failure | 映射稳定错误；UserDefaults/文件中没有 Key |
| malformed stream | 映射协议错误；已有 partial 时标记 incomplete |
| secret hygiene | fixture、snapshot、日志和 `safeDetail` 不包含 sentinel Key |
| 连接测试 | adapter 的 `connectionTest` intent 不发送捕获正文；设置页 testing/success/error 状态仍待连接测试按钮任务 |
| stale run isolation | 旧 run 的迟到事件不能覆盖新 run |
| 输入过大 | 不自动分块，给出选区/短页面恢复动作 |

## 8. V0.2 后续任务拆分

### 任务 A：Provider profile 与 Keychain secret boundary（已实现）

- **用户可观察结果**：设置页能保存 Base URL、模型名和 API Key；重开 APP 后显示非敏感配置与“Key 已保存”，但不回显完整 Key。
- **只做**：ProviderProfile、profile store port/UserDefaults adapter、SecretStore port/Keychain adapter、配置状态和失败恢复。
- **明确不做**：模型请求、streaming、SQLite、多 Provider、连接测试。
- **主要文件区域**：`LinkDigestCore/ProviderModels.swift`、`ModelPorts.swift`、`LinkDigestAdapters/*Store.swift`、`LinkDigestApp/ProviderSettingsView.swift`。
- **验证方式**：fake store 单测、Keychain 独立 test service 集成测试、重启配置恢复、secret scan。
- **学习重点（≤5）**：ProviderProfile、SecretStore、Keychain、opaque reference、adapter。

### 任务 B：OpenAI-compatible streaming adapter 与 fake server（adapter 与自动验证已实现）

- **本轮工程结果**：Core 已提供 ModelProvider port、stream event 与稳定失败；adapter 已由 loopback fake server 验证。设置页“测试连接”与 testing/success/failure 状态留给后续小任务，不把完整 Key 引入 ViewModel state。
- **只做**：URL 构造、Chat Completions request、SSE decoder、有界重试、取消传播与 fake server；连接测试 intent 已定义但尚未接入 UI。
- **明确不做**：总结/翻译 UI、SQLite、Responses API、Ollama、真实 Provider 自动测试。
- **主要文件区域**：`LinkDigestCore/ModelProvider.swift`、`LinkDigestAdapters/OpenAICompatibleProvider.swift`、`ChatCompletionsStreamDecoder.swift`、`LinkDigestAdaptersTests`。
- **验证方式**：loopback fake server 覆盖 streaming、401、429、5xx、malformed、cancel、secret hygiene。

## 9. 系统性风险与恢复成本

### 9.1 SwiftUI 直接访问 Keychain/URLSession

短期看少几个文件，长期会把界面生命周期、秘密存储、网络重试和取消绑在一起。设置页或窗口重建可能重复请求，测试必须启动真实平台能力，未来换 UI 或 adapter 时需要重写整条链。

恢复成本：先补 port，再把 View 中的副作用逐个迁出；迁移期间容易出现双请求与状态不同步。因此必须在第一个 BYOK 任务就建立 Orchestrator/port/adapter。

### 9.2 API Key 进入日志或 fixture

日志、CI artifact、截图和 Git 都可能长期复制秘密，单纯“之后删除”无法保证所有副本消失，也可能产生 Provider 费用和账号风险。

恢复成本：立即吊销 Key、清理历史与缓存、检查 CI/备份并轮换凭据。预防成本远低于事后恢复，因此测试只使用虚构 sentinel，错误映射只保留 allowlist 字段。

### 9.3 Cancellation 没有传到 URLSession

UI 虽显示已停止，网络仍继续消耗 token、带宽和费用，迟到事件还可能覆盖新任务。

恢复成本：需要同时修复 Task ownership、URLSession cancellation、run identifier 与 MainActor 状态过滤。规划从一开始就要求端到端 cancellation 和 stale-run 隔离。

### 9.4 V0.1 Edge 未关闭就推进 V0.2

如果浏览器捕获与模型调用同时失败，排错会跨越 Extension、Host、socket、APP、Keychain 和 Provider 六层，无法快速判断是输入没到达还是模型链失败。

恢复策略：V0.2 规划和隔离单元任务可以先进行，但在 V0.2 浏览器到模型的集成验收前，应先补齐 Edge，或由 Syc 明确接受两条未关闭矩阵并分别保存证据。任何情况下都不能把 V0.1 标记为已关闭。

### 9.5 现在引入 SQLite

V0.2 只需要一个 profile 与当前内存 Run。此时引入 SQLite 会把 Provider、migration、历史模型和恢复模式绑成一个任务，扩大测试与许可证 spike。

恢复成本：一旦 UI/Orchestrator 直接依赖具体表结构，V0.3 很难独立调整历史模型。V0.2 使用 `ProviderProfileStore` port；UserDefaults 只保存非敏感 profile，V0.3 再替换为 SQLite adapter。

## 10. 依赖与许可证计划

V0.2 推荐不新增第三方依赖：

- 网络与 streaming：Foundation/URLSession。
- Keychain：Apple Security framework。
- 并发与取消：Swift Concurrency。
- fake server：Apple Network.framework/Foundation。

如果实现阶段发现必须新增依赖，任务应暂停在依赖评估，记录：

1. 当前原生能力缺口。
2. 候选依赖及许可证。
3. GPL/AGPL/非商业/UNKNOWN 检查。
4. 不引入依赖的替代方案。
5. Apple Silicon、Debug/Release、签名和测试验证方式。

## 11. 实施顺序与关闭门禁

建议顺序：A → B → C → D。每个任务都按 `docs/TASK_TEMPLATE.md` 在实施时完成工程证据和过程讲解。

V0.2 只能在以下条件同时满足后标记完成：

- 单个 profile 与 Keychain secret boundary 已验证。
- fake server 覆盖成功、401、429/5xx、断流、malformed、取消和 secret hygiene。
- 总结与翻译 streaming 可观察，停止传播到底层。
- 完整与 incomplete 结果语义明确。
- Debug/Release 构建与 doctor 无 FAIL。
- 不依赖 LinkDigest 账号、Cloud API、SQLite、导出或真实 Provider 自动测试。

V0.1 Edge 未完成时，V0.2 可以形成隔离组件证据，但不得借此宣称浏览器矩阵或 V0.1 已关闭。

任务 A–D 当前已满足上述 V0.2 工程关闭门禁；逐项证据集中记录在 `docs/specs/V0.2_BYOK_ACCEPTANCE.md`。这不改变 V0.1 Edge、V0.3 SQLite/历史或 V0.4 导出的独立状态。
