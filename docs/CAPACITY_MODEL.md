# LinkDigest 容量模型（远期参考）

> 状态：保留但延后。这里的数字是未来进入账号、同步和托管模型阶段后可重新校准的压测基线，不是 P0 要求、当前真实用户量或购买服务器的指令。

P0 以 macOS 原生 local-first 闭环为唯一范围。本文不得用于要求当前实现 Fastify、PostgreSQL、队列、微服务或多区域部署。

## 1. 为什么需要容量模型

“100 万注册用户”只描述数据库里可能存在多少账号，不能直接说明服务器压力。真正决定系统压力的是活跃用户、峰值同时在线、每个在线用户多久访问一次云端、同步多少数据、托管模型任务有多少，以及这些行为是否集中在同一时间。

容量模型负责把产品目标换成可测的请求、任务、连接和数据量，再为扩容提供触发条件。

## 2. 名词与口径

| 名词 | 人话定义 | 本项目用途 |
|---|---|---|
| Registered Users | 曾经建立过账号的累计用户 | 商业目标，不直接等于负载 |
| MAU | 30 天内至少使用一次的用户 | 判断月度活跃规模 |
| DAU | 一天内至少使用一次的用户 | 判断日常使用规模 |
| Peak Concurrent | 高峰时同时保持活跃会话的用户 | 估算连接、缓存和请求并发 |
| RPS | 每秒到达 API 的请求数量 | API 压测与横向扩容口径 |
| Job Intake | 每秒进入异步队列的任务数 | 托管模型、同步和删除队列入口压力 |
| SLO | 对延迟、可用性和恢复能力的可测目标 | 判断服务是否真的“稳定” |

本地提取、SQLite 查询和 BYOK 模型调用不计入 LinkDigest 云端 RPS，因为它们在用户设备或用户自己的 Provider 上运行。

## 3. 规划基线

| 阶段 | 注册用户 | MAU | DAU | 峰值在线 | 定位 |
|---|---:|---:|---:|---:|---|
| 公开测试 | 10,000 | 3,000 | 800 | 100 | 验证真实行为和成本 |
| 10 万准备度 | 100,000 | 30,000 | 8,000 | 1,000 | 多实例、限流、备份恢复可验证 |
| 100 万准备度 | 1,000,000 | 300,000 | 80,000 | 10,000 | 通过峰值压测和数据规模测试 |

这些比例是保守的设计假设，不是增长预测。获得真实数据后，必须保留用户量目标，更新行为比例和压测输入。

## 4. API 负载怎么算

规划公式：

```text
目标 RPS
= 峰值在线用户
  x 每个用户每分钟云端请求数
  / 60
  x 突发系数
```

100 万准备度使用以下保守上限：

```text
10,000 峰值在线
x 2 次云端请求/分钟
/ 60
x 3 倍突发
= 1,000 RPS
```

“2 次云端请求/分钟”只包含账号、权益、同步 manifest、远程配置和托管任务状态，不包含本地 UI 操作。3 倍突发用于覆盖应用更新、活动发布和网络恢复后的集中重试。

### 4.1 分阶段压测

| Profile | 持续负载 | 突发负载 | 目的 |
|---|---:|---:|---|
| Developer | 20 RPS / 10 分钟 | 50 RPS / 1 分钟 | 发现明显阻塞和错误 |
| Public Beta | 100 RPS / 30 分钟 | 300 RPS / 5 分钟 | 验证公开测试部署 |
| 10 万准备度 | 300 RPS / 2 小时 | 600 RPS / 15 分钟 | 验证稳定扩容、连接池与限流 |
| 100 万准备度 | 500 RPS / 2 小时 | 1,000 RPS / 15 分钟 | 验证峰值、不丢写请求和自动恢复 |

压测必须使用合成账号、合成 URL 和合成密文，不使用真实用户正文、Key、Cookie 或账号资料。

## 5. 异步任务容量

目标入口为 100 jobs/s。这是“API 能安全接收并持久化任务”的短时上限，不代表同时向模型 Provider 发出 100 次推理。

```text
API 接收任务
   |
   v
PostgreSQL transaction：job + entitlement reservation + outbox
   |
   v
Queue 调度
   |
   v
Worker 按 Provider 配额、用户额度和全局成本上限消费
```

队列必须吸收突发，worker 并发由 Provider 限额和预算控制。取消、失败或超时后，Usage Ledger 追加退款或释放记录，不覆盖原消费历史。

### 5.1 队列 SLO

| 指标 | 10 万准备度 | 100 万准备度 | 劣化触发 |
|---|---:|---:|---:|
| 任务接收 p95 | <= 500 ms | <= 500 ms | > 1,000 ms |
| 普通队列年龄 p95 | <= 30 s | <= 60 s | 连续 10 分钟超标 |
| 任务重复落库 | 0 | 0 | 任意重复即失败 |
| 额度错扣率 | 0 | 0 | 任意无法自动对账即停止托管入口 |

模型完成时间受外部 Provider 影响，必须单独展示，不伪装成 LinkDigest 自己的 API 延迟。

## 6. 数据规模

100 万准备度的合成数据集：

| 数据 | 数量假设 | 设计目的 |
|---|---:|---|
| User | 1,000,000 | 验证身份和权益查询索引 |
| Device | 3,000,000 | 平均每用户最多 3 个已登记设备 |
| Sync metadata | 100,000,000 | 平均每用户 100 条同步索引/版本记录 |
| Usage ledger | 100,000,000 | 验证只追加流水、对账和归档路径 |
| Encrypted blob | 不预设平均正文大小 | 对象存储按真实启用率与大小分布测量 |

原文和摘要不进入 PostgreSQL 大字段。开启同步后，PostgreSQL 只保存 blob ID、版本、校验和、大小、所有者和删除状态；密文进入对象存储。

### 6.1 数据扩展触发条件

- 单表达到 50,000,000 行时开始进行分区/归档压测，不自动分区。
- 常用查询 p95 连续三次压测高于 100 ms 时，先检查索引和查询计划，再考虑读副本。
- 数据库连接使用率持续高于池上限的 70% 时，先检查连接泄漏和事务长度，再增加实例或池容量。
- 备份恢复没有通过规定 RPO/RTO 时，不允许用“增加副本”代替恢复验证。

## 7. 服务 SLO

这些 SLO 只约束 LinkDigest 控制的非模型云端接口：

| 指标 | 公开测试 | 10 万准备度 | 100 万准备度 | 劣化阈值 |
|---|---:|---:|---:|---:|
| API availability（月） | 99.5% | 99.9% | 99.95% | 低于对应目标 |
| 普通 API p95 | <= 500 ms | <= 300 ms | <= 300 ms | > 800 ms |
| 普通 API p99 | <= 1,500 ms | <= 800 ms | <= 800 ms | > 2,000 ms |
| API 5xx 比例 | < 1.0% | < 0.5% | < 0.2% | 超标 5 分钟 |
| Remote Config p95 | <= 500 ms | <= 200 ms | <= 200 ms | > 500 ms |
| Sync Manifest p95 | <= 800 ms | <= 500 ms | <= 500 ms | > 1,000 ms |
| RPO | <= 24 h | <= 15 min | <= 5 min | 恢复演练未达到 |
| RTO | <= 8 h | <= 4 h | <= 1 h | 恢复演练未达到 |

本地核心另有独立指标：桌面冷启动、DOM 捕获、SQLite 查询和扩展交接不能被云端 SLO 掩盖。

## 8. 扩容与拆分信号

| 现象 | 先做什么 | 仍不达标时 |
|---|---|---|
| API CPU 持续 > 65% 或 p95 超标 | 增加无状态 API replica，检查慢 route | 按模块 profiling，评估拆出热点模块 |
| 数据库查询 p95 > 100 ms | 查询计划、索引、缩短事务 | 读副本、归档或分区验证 |
| Queue age 持续 > 60 s | 按 Provider 配额增加 worker | 拆分队列优先级或独立 worker pool |
| 单模块故障拖垮其它接口 | timeout、bulkhead、circuit breaker | 拆成独立服务并保留原 contract |
| 对象存储或模型成本失控 | 配额、压缩、保留期限、用户提示 | 调整套餐或停止高成本入口 |

微服务不是注册量达到某个数字时自动触发。只有资源曲线、故障隔离或团队所有权提供证据时才拆分。

## 9. 可观测性与成本护栏

### 9.1 必须采集

- API：RPS、p50/p95/p99、4xx/5xx、active requests。
- PostgreSQL：连接数、query latency、lock wait、存储增长、备份状态。
- Queue/worker：入队、完成、重试、失败、queue age、provider throttling。
- Managed AI：每 Provider 请求数、Token/费用、预留与结算差异。
- Sync：manifest 冲突率、blob 上传失败、删除队列年龄。

### 9.2 禁止采集

- API Key、Cookie、Token、私钥。
- 原文、摘要、prompt、模型输出。
- 完整私人 URL、浏览器历史和用户本机路径。
- 可直接重建用户阅读内容的高基数字段。

### 9.3 成本保护

- 托管模型先预留额度，再执行，完成后结算，失败自动释放或退款。
- 每用户、每套餐、每 Provider 和全局预算都有独立限额。
- 当日成本达到预算的 80% 时报警；达到 100% 时停止新托管任务，BYOK 和本地功能继续可用。
- 不为容量目标预购生产资源。先用压测验证架构，再根据真实 MAU、RPS 和成本扩容。

## 10. 失败与恢复

| 故障 | 用户仍可使用 | 系统恢复动作 |
|---|---|---|
| Cloud API 不可用 | 本地提取、BYOK、历史、导出 | 本地排队可重试的同步操作，显示云端状态 |
| PostgreSQL 短暂故障 | 全部本地能力 | API fail closed，不从缓存伪造权益或计费事实 |
| Queue 丢失 | 本地与已完成云任务 | 从 PostgreSQL job/outbox 重建待处理任务 |
| 对象存储不可用 | 本地内容、账号与权益 | 暂停 blob 上传，不删除本地副本 |
| 模型 Provider 限流 | 本地历史、导出、其它 Provider | 延迟重试、切换 BYOK 或退回额度 |

## 11. 本阶段验证

### 工程检查

1. 架构图中的每个有状态组件都能指出唯一事实来源。
2. 1,000 RPS 和 100 jobs/s 均有公式、测试时长和失败阈值。
3. 注册用户量、MAU、DAU、峰值在线和 RPS 没有混为一谈。
4. 本地功能和云端能力的 SLO 分开定义。

### 可选跟做（5–15 分钟，不阻塞开发）

1. 打开本文第 3 节，用自己的话说明“100 万注册”为什么不等于“100 万人同时请求”。
2. 用第 4 节公式重新计算：如果峰值在线改成 5,000，其它参数不变，目标应为 500 RPS。
3. 打开第 10 节，指出 Cloud API 故障时用户仍能做的四件事。
4. 故意把“注册用户”误当成“峰值在线”代入公式，观察 RPS 会被放大到 100,000；这就是容量口径错误会造成的过度建设。
5. 恢复方式：重新使用“峰值在线”作为公式入口，并在获得真实数据后只调整行为假设，不推翻组件边界。
